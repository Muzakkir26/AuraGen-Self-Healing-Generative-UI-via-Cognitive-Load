## Concerns (important before any review)
1. **The tests don't touch our code.** For example, `test_api_and_schemas.py` defines its own Python `ASTSchemaValidator` class and tests that, using different component names (`Container`, `Input`, `QuantumWidget`). The real validator is `ai/validator/astValidator.js` and the real API is `server/`.
2. **The benchmark numbers are simulated.** `evaluate_performance.py` generates "1,000 sessions" with `random.gauss(...)`. Presenting these as measured results would be misleading at review.
3. **The bug tracker lists bugs as "resolved & verified" in parts that don't exist yet** (LLM stream, responsive layout adapter, DOM patching engine).
4. **The final report and deck are written before the project is built.** They describe features and results that aren't real yet.
5. **All work landed on one day** (Nov 14), through web uploads. Only 1 commit day so far. There's also a duplicate file, `Test_Plan/generate_test_plan.py.py`.
6. Not merged into `main`, and the files sit at the repo root rather than in `/tests`.

## Next (suggested)
1. Move the work into `/tests` and keep the test-case spreadsheets.
2. Replace mock tests with tests against the real code: call `server/` endpoints with real payloads, and run real and malicious samples through `ai/validator`.
3. Label every simulated number as "target" or "projected" until it's measured. Produce real numbers once the end-to-end demo runs (pass rate of generated components, latency).
4. Commit small pieces daily from the local git client instead of bulk web uploads.
